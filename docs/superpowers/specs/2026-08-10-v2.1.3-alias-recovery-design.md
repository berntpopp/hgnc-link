# HGNC Link v2.1.3 Alias Recovery Design

## Context

The signed `v2.1.3` tag, immutable GitHub release, release assets, source-SHA
container alias, provenance, and SBOM attestations are complete. The first
release run failed while uploading one draft asset with a transient GitHub 404.
Its recovery path then exposed an ORAS 1.3.3 command-line bug in the pinned
reusable workflow. The only missing publication is the `2.1.3` GHCR alias that
must point at the already accepted source manifest digest.

## Chosen approach

Add a one-shot, manually dispatched workflow to `hgnc-link`. It uses GitHub's
short-lived workflow token because the local operator token intentionally lacks
`packages: write`. The job is protected by the existing `release` environment
and grants only `contents: read` and `packages: write`.

The workflow is hard-coded to the immutable recovery tuple:

- source revision: `0f318f20ba6ecf81682919718a416e018f84fe98`
- source alias: `sha-0f318f20ba6ecf81682919718a416e018f84fe98`
- release tag: `v2.1.3`
- version alias: `2.1.3`
- accepted digest: `sha256:1b9f67c4d072dc84071fa65e72bebb8449df9935504bc4e7e9c398719eb6f31a`

There are no user inputs, deployment steps, tag changes, image rebuilds, or
deletion paths.

## Recovery flow

1. Install checksum-pinned GitHub CLI 2.96.0 and ORAS 1.3.3.
2. Cryptographically verify the published `v2.1.3` GitHub release.
3. Resolve the source alias and require its digest to equal the accepted digest.
4. Fetch the OCI config with valid ORAS 1.3.3 syntax and require its source
   revision label to equal the signed release revision.
5. If `2.1.3` already exists, require it to match. Otherwise copy the source
   alias to `2.1.3`, which preserves identical manifest bytes.
6. Resolve `2.1.3` again and fail unless it equals the accepted digest.

## Verification and removal

A focused static test will fail before the workflow exists and then enforce the
manual-only trigger, minimal permissions, protected environment, immutable
tuple, checksum pins, release verification, revision verification, absence of
deployment commands, and digest equality after the copy.

After the focused test, full local CI, and remote PR checks pass, the workflow
will be merged and dispatched once. The release alias will be queried directly
from GHCR and compared to the accepted digest. A cleanup PR will then delete the
one-shot workflow and its focused test, leaving this design and the audit trail
but no standing package-write recovery entry point.

## Alternatives rejected

- Moving or recreating `v2.1.3` would violate immutable tag policy.
- Rebuilding the image would discard the already accepted manifest identity.
- Patching the shared router and cutting a different HGNC release is broader
  than the single missing alias and does not repair the existing `v2.1.3`
  publication.
- Expanding the local token to `write:packages` is unnecessary when the
  repository's protected release environment already provides least-privilege
  credentials and review.
